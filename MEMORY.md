## 2. Что из Seller Central доступно через API

Проверено живыми запросами к аккаунту 2026-08-11, а не по документации.

### Доступно

| Данные | Источник |
|---|---|
| Выручка и все комиссии | Finances API, `listFinancialEvents` |
| Stranded inventory | `GET_STRANDED_INVENTORY_UI_DATA` |
| Статусы товаров | `GET_MERCHANT_LISTINGS_ALL_DATA` |
| Account Health | `GET_V2_SELLER_PERFORMANCE_REPORT` |
| Отзывы о продавце | `GET_SELLER_FEEDBACK_DATA` |
| Показатели FBA, излишки | `GET_FBA_INVENTORY_PLANNING_DATA` |
| Цены конкурентов | `/products/pricing/v0/competitivePrice` |

### Недоступно, и обхода нет

| Данные | Почему |
|---|---|
| Виджет Actions на Home | не выведен в API, собирается из других разделов |
| История Performance Notifications | Notifications API только на отправку новых событий, нужен приёмник в AWS |
| Входящие Messages | Messaging API умеет лишь отправлять письмо покупателю по заказу |
| Customer Reviews | Amazon не отдаёт отзывы о товарах ни в одной версии SP-API |
| Кейсы поддержки | публичного API не существует |
| Pricing Health как виджет | виджета нет, но конкурентную цену можно сравнивать самостоятельно |

Строки `ACCOUNT_HEALTH` и `PRICING_HEALTH` в справочнике типов отчётов не
встречаются вообще — искать их бесполезно.

## 3. Подвохи Amazon

### `CANCELLED` — это «данных нет»

Отчёт получает статус `CANCELLED` не только при явной отмене, но и
автоматически, когда возвращать нечего. Отчёт по зависшим запасам
отменяется именно тогда, когда запасы в порядке. Как ошибку это трактовать
нельзя.

### Статус показателя `NONE` — тоже отсутствие данных

В `GET_V2_SELLER_PERFORMANCE_REPORT` подветки `invoiceDefectRate` приходят со
статусом `NONE`. Проверка «всё, что не GOOD — проблема» объявляла аккаунт с
рейтингом 1000 из 1000 неисправным. Проблемными считаются только явно плохие
статусы: `FAIR`, `POOR`, `AT_RISK`, `CRITICAL`, `DEFICIENT`, `UNHEALTHY`.

### Структура отчёта о показателях продавца

```
accountStatuses[]        marketplaceId, status (NORMAL / …)
performanceMetrics[0]
  lateShipmentRate       { status, targetValue, targetCondition, rate, …Count }
  orderDefectRate        { afn: {...}, mfn: {...} }   — разбит по типу доставки
  accountHealthRating    { ahrStatus, ahrScore }
  warningStates[]
```

Значение метрики лежит в `rate` у долевых и в поле с суффиксом `Count` у
штучных. Единого поля нет.

### Две независимые отметки прогресса

`lastPostedBefore` — докуда добор догнал текущий момент.
`reachedThrough` — докуда доехала выгрузка истории.

Пока они писались в одно поле, каждый запуск крона сдвигал отметку истории на
сегодня, и режим `resume` начинал с сегодняшнего дня. Полгода данных не
собрались бы никогда.

### Лимит Finances API

0,5 запроса в секунду. За год набирается около четырёх тысяч страниц — это
примерно пять часов. Многочасовой прогон в Actions вытесняется следующим
запуском по расписанию, а коммит происходит только после выхода из скрипта,
поэтому снятый прогон терял всю работу. Отсюда `--max-chunks`.

## 4. Форматы данных

### `data/finance.json`

Проводки: дата × площадка × валюта × статья × тип Amazon. Суммы **не
пересчитываются** между валютами — курса в данных Amazon нет, а взятый со
стороны не сойдётся ни с Seller Central, ни с банком.

Статьи расходов: `fee_referral`, `fee_fba`, `fee_placement`, `fee_storage`,
`fee_inbound`, `fee_ads`, `fee_promo`, `fee_other`. Незнакомый тип попадает в
`other` под своим именем и печатается списком — так новая комиссия Amazon не
исчезнет молча.

### `data/account-health.json`

По записи на проверку: `id`, `status` (`ok` / `warn` / `error` /
`unavailable`), `count`, `items`, `message`, `extra`.

### `data/sync-log.json`

Общий журнал для всех интеграций. Запись пишется и при успехе, и при провале:
сбой без следа выглядит как «данные почему-то старые».

### `data/listings-snapshot.json`

Снимок статусов товаров с прошлой проверки. Само по себе «неактивен» ни о чём
не говорит — важно изменение, поэтому сравниваются снимки.
