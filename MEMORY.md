## 2. Что из Seller Central доступно через API

Проверено живыми запросами к аккаунту 2026-08-11, а не по документации.

### Доступно

| Данные | Источник |
|---|---|
| Выручка и все комиссии | Finances API, `listFinancialEvents` |
| Stranded inventory | `GET_STRANDED_INVENTORY_UI_DATA` |
| Статусы товаров | `GET_MERCHANT_LISTINGS_ALL_DATA` |
| Account Health | `GET_V2_SELLER_PERFORMANCE_REPORT` |
| Отзывы о продавце | `GET_SELLER_FEEDBACK_DATA` |
| Показатели FBA, излишки | `GET_FBA_INVENTORY_PLANNING_DATA` |
| Цены конкурентов | `/products/pricing/v0/competitivePrice` |

### Недоступно, и обхода нет

| Данные | Почему |
|---|---|
| Виджет Actions на Home | не выведен в API, собирается из других разделов |
| История Performance Notifications | Notifications API только на отправку новых событий, нужен приёмник в AWS |
| Входящие Messages | Messaging API умеет лишь отправлять письмо покупателю по заказу |
| Customer Reviews | Amazon не отдаёт отзывы о товарах ни в одной версии SP-API |
| Кейсы поддержки | публичного API не существует |
| Pricing Health как виджет | виджета нет, но конкурентную цену можно сравнивать самостоятельно |

Строки `ACCOUNT_HEALTH` и `PRICING_HEALTH` в справочнике типов отчётов не
встречаются вообще — искать их бесполезно.

## 3. Подвохи Amazon

### `CANCELLED` — это «данных нет»

Отчёт получает статус `CANCELLED` не только при явной отмене, но и
автоматически, когда возвращать нечего. Отчёт по зависшим запасам
отменяется именно тогда, когда запасы в порядке. Как ошибку это трактовать
нельзя.

### Статус показателя `NONE` — тоже отсутствие данных

В `GET_V2_SELLER_PERFORMANCE_REPORT` подветки `invoiceDefectRate` приходят со
статусом `NONE`. Проверка «всё, что не GOOD — проблема» объявляла аккаунт с
рейтингом 1000 из 1000 неисправным. Проблемными считаются только явно плохие
статусы: `FAIR`, `POOR`, `AT_RISK`, `CRITICAL`, `DEFICIENT`, `UNHEALTHY`.

### Структура отчёта о показателях продавца

```
accountStatuses[]        marketplaceId, status (NORMAL / …)
performanceMetrics[0]
  lateShipmentRate       { status, targetValue, targetCondition, rate, …Count }
  orderDefectRate        { afn: {...}, mfn: {...} }   — разбит по типу доставки
  accountHealthRating    { ahrStatus, ahrScore }
  warningStates[]
```

Значение метрики лежит в `rate` у долевых и в поле с суффиксом `Count` у
штучных. Единого поля нет.

### Отчёт по заказам ограничен 30 днями и молчит об этом

`GET_FLAT_FILE_ALL_ORDERS_DATA_BY_ORDER_DATE_GENERAL` отдаёт максимум 30 дней
за запрос. О превышении Amazon **не сообщает ошибкой**: отчёт получает статус
`DONE`, а в теле вместо таблицы лежит одна строка

```
Date range exceeded. Report can be requested only upto 30 days
```

Разобранная как обычный TSV, она даёт ноль строк — то есть «продаж не было»
вместо «выгрузка не удалась». Наступили на это 2026-08-19: сборщик записал
пустой файл и поставил в журнал `ok`.

Проверять надо заголовок тела, а не только статус отчёта, а квартал резать на
куски по 30 дней. Пустой результат у аккаунта с оборотом — это сбой, и файл
перезаписывать нельзя.

### В `SALES_AND_TRAFFIC` разрез по ASIN не имеет даты

`GET_SALES_AND_TRAFFIC_REPORT` выглядит идеальным источником недельных продаж:
в нём есть и `parentAsin`, и `dateGranularity: WEEK`. Но гранулярность делит на
недели **только** блок `salesAndTrafficByDate`. Блок `salesAndTrafficByAsin`
приходит одним итогом за весь период, поля даты в его строках нет вообще
(проверено живым запросом 2026-08-19: 14 строк по датам против 37 строк по
ASIN без дат).

Недельные продажи в разрезе ASIN означали бы отчёт на неделю на площадку:
13 × 13 = 169 отчётов при лимите три запроса на пять минут — около пяти часов.
Поэтому источник продаж по товарам — отчёт по заказам, а не этот.

### Отчёты по купонам и дилам принимают ровно одну площадку

`GET_COUPON_PERFORMANCE_REPORT` и `GET_PROMOTION_PERFORMANCE_REPORT` — не как
отчёт по заказам, который берёт список. Список из тринадцати даёт отчёт со
статусом **FATAL**, а причина лежит **в теле отчёта**, а не в ответе API:

```json
{"reportRequestError":"Required number of marketplaces should be 1 but actual was 13."}
```

Отсюда два правила: обходить площадки по одной и при FATAL всё равно
скачивать тело — иначе в логе остаётся «отчёт завершился со статусом FATAL»,
что не объясняет ничего.

Отказ одной площадки не должен ронять остальные: у части площадок роли или
акций может не быть вовсе, а одна отметка на графике лучше, чем ноль отметок
из-за соседа. Такой сбор помечается в журнале как `partial`, а не `ok`.

### Отчёты по акциям фильтруют по дате старта, а не по пересечению

Кампания, начавшаяся до окна и дожившая до него, в выборку по точным датам
периода не попадёт — и неделя останется без отметки, хотя акция шла. Старт
запрашивается с запасом назад (`START_LOOKBACK_DAYS`).

Обратный край тоже есть: купон может кончаться позже конца данных. На отметки
это не влияет, но при подсчёте эффекта кампанию обязательно обрезать по концу
периода — иначе «ожидание» считается на дни без выгрузки.

### Отменённый дил — не событие

У дилов бывает статус `CANCELED` (в выгрузке 2026-08-04 их было 3 из 18).
Отметить им неделю значит показать акцию, которой не было. В данные идут
только состоявшиеся: `APPROVED`, `RUNNING`, `COMPLETED`, `ACTIVE`.

### Родительский ASIN свой на каждой площадке

У `B0854MW97N` родитель в DE `B0FCXS9PDP`, в NL `B0F4DVM11Y`, в PL
`B0F6N6D6N2`, в SA `B0DWGT8RJZ`, а во FR родителя нет совсем. Проверено
`getCatalogItem` с `includedData=relationships` сразу по всем площадкам —
`marketplaceIds` принимает список, и связи возвращаются блоком на каждую.

Фильтр «Parent» по сырому значению давал бы на каждой площадке свой набор.
Поэтому дети, у которых хоть на одной площадке общий родитель, сшиваются в
**семью вариаций** (класс эквивалентности, `build_families`).

### Две независимые отметки прогресса

`lastPostedBefore` — докуда добор догнал текущий момент.
`reachedThrough` — докуда доехала выгрузка истории.

Пока они писались в одно поле, каждый запуск крона сдвигал отметку истории на
сегодня, и режим `resume` начинал с сегодняшнего дня. Полгода данных не
собрались бы никогда.

### Лимит Finances API

0,5 запроса в секунду. За год набирается около четырёх тысяч страниц — это
примерно пять часов. Многочасовой прогон в Actions вытесняется следующим
запуском по расписанию, а коммит происходит только после выхода из скрипта,
поэтому снятый прогон терял всю работу. Отсюда `--max-chunks`.

## 4. Форматы данных

### `data/finance.json`

Проводки: дата × площадка × валюта × статья × тип Amazon. Суммы **не
пересчитываются** между валютами — курса в данных Amazon нет, а взятый со
стороны не сойдётся ни с Seller Central, ни с банком.

Статьи расходов: `fee_referral`, `fee_fba`, `fee_placement`, `fee_storage`,
`fee_inbound`, `fee_ads`, `fee_promo`, `fee_other`. Незнакомый тип попадает в
`other` под своим именем и печатается списком — так новая комиссия Amazon не
исчезнет молча.

### `data/weekly-sales.json`

Агрегаты неделя × площадка × ASIN за 14 недель (13 полных + текущая). Строка:
`w` — индекс недели, `m` — код площадки, `a` — ASIN, `u` — штуки, `r` — деньги,
`d` — скидка промо, `o` — заказов.

Рядом: `weeks` (с флагом `partial` у текущей), `marketplaces` (имя и валюта),
`families` (семьи вариаций), `asins` (название, бренд, семья).

Идентификаторов заказов и данных покупателей в файле нет — репозиторий
публичный. `unpricedUnits` — штуки из продаж вне Amazon: этот канал приходит в отчёте
без цены и валюты (проверено: все строки без цены — `Non-Amazon`, и наоборот).
Они попали в штуки, но не в деньги, и разница показана в интерфейсе.

### `data/promotions.json`

Кампании, пересекающиеся с окном раздела продаж: `kind` (`coupon`,
`best_deal`, `lightning_deal`), `start`, `end`, `m` (площадка), `asins`,
`units`, `sales`, у купона ещё `discount`.

Нужен отметкам над столбцами в разделе продаж. Отметка ставится при
пересечении кампании с неделей хотя бы одним днём и уважает фильтры: при
выбранном товаре отмечаются только его акции.

Масштаб на 2026-08-19: **484 кампании на десяти площадках** за 13 недель.
Купоны идут практически каждую неделю (47–123 в неделю по всем площадкам),
поэтому их отметка почти постоянна; различают недели бест-дилы — от 0 до 23.
Отсюда счёт кампаний прямо в подсказке: без него постоянный значок ничего
не сообщает. Список в подсказке обрезан до восьми крупнейших — полный
нечитаем.

### `data/fx-rates.json`

Справочные курсы ЕЦБ: `{дата: {валюта: курс}}`, курс — единиц валюты за один
евро. Только рабочие дни, 90-дневный ряд. Источник внешний по отношению к
Amazon: курса в данных Amazon нет ни в одном отчёте.

Нужен режиму «Всё в евро» в разделе продаж. Пересчёт понедельный, среднее по
рабочим дням недели. Режим подписан как оценка: Amazon конвертирует по своему
курсу на момент выплаты, и с Seller Central цифра не сойдётся.

### `data/wiki/`

Статьи вики: `index.json` (указатель) и `<имя>.<язык>.md` (тела). Поле `langs`
перечисляет языки, на которых статья **действительно** есть; при отсутствии
перевода статья открывается на русском с пометкой.

### `data/account-health.json`

По записи на проверку: `id`, `status` (`ok` / `warn` / `error` /
`unavailable`), `count`, `items`, `message`, `extra`.

### `data/sync-log.json`

Общий журнал для всех интеграций. Запись пишется и при успехе, и при провале:
сбой без следа выглядит как «данные почему-то старые».

### `data/listings-snapshot.json`

Снимок статусов товаров с прошлой проверки. Само по себе «неактивен» ни о чём
не говорит — важно изменение, поэтому сравниваются снимки.

**2026-08-11.** Сбор истории за февраль–июль отменён по запросу. Раздел

**2026-08-19.** Добавлены разделы «Продажи по неделям» и «Вики».

Источником продаж по товарам выбран отчёт по заказам, а не
`GET_SALES_AND_TRAFFIC_REPORT`: у второго разрез по ASIN без дат (см. выше).

«Вместе по всем маркетплейсам» считается в **штуках**: они складываются по
всем тринадцати площадкам без курса. Деньги показываются отдельной строкой на
каждую валюту — решение не пересчитывать валюты подтверждено, а не отменено.

Разбор markdown для вики написан свой (`assets/js/markdown.js`): стек без
сборки, CDN недоступен, а держать в репозитории чужой минифицированный файл
означает зависимость, которую никто не читает. Дерево собирается через
`createElement`/`textContent`, `innerHTML` не используется.

Появился `tools/mount-check.mjs` — монтаж раздела в headless-DOM с проверкой
трёх языков, смены фильтров и уборки наблюдателей. `jsdom` намеренно не в
зависимостях: на Pages он не нужен, Actions собирают данные, а не страницу.

**2026-08-19, вечер.** Настройки, журнал и перевод в евро.

Переключатели языка и темы стояли тремя копиями прямо в вёрстке `index.html`,
`app.html` и `logs.html`. Добавить к ним часовой пояс значило бы завести
четвёртую копию, поэтому они собраны в одно окно (`assets/js/settings.js`) с
кнопкой в правом верхнем углу на всех трёх страницах.

**Часовой пояс применяется только к моментам времени.** Календарная дата
`2026-05-18` разбирается как полночь UTC, и в поясе западнее Гринвича стала бы
17 мая — недели на графике поехали бы у половины пользователей. Разделение
сделано в `format.js`: строка вида `YYYY-MM-DD` форматируется в UTC всегда.

Перевод в евро добавлен по прямой просьбе. Решение «не пересчитывать валюты»
остаётся значением по умолчанию и целиком сохраняется в `finance.js`; в
разделе продаж появился отдельный режим по курсам ЕЦБ, подписанный как
оценка. Курс берётся понедельно средним по рабочим дням, валюта без курса
называется в сноске, а не обнуляется молча.

Колокольчик показывает десять последних запусков с тем, какие данные приехали
(`describeStats`). Незнакомая ошибка больше не остаётся без причины: если
разобрать код не удалось, показывается техническая формулировка.

**2026-08-19, поздний вечер.** Отметки акций над неделями.

Формой, а не цветом: круг — купон, ромб — бест-дил, треугольник —
молниеносный. Отметки лежат поверх цветных столбцов, и ещё один цвет там
читался бы как очередная серия. Значок рядом с галочкой повторяет форму —
иначе связать настройку с рисунком можно только угадыванием.

Отметки стоят на одной высоте у всех недель, в отдельной полосе над полем
графика. Скачущие по вершинам столбцов, они читались бы как ещё один ряд
данных.

Галочки строятся по тому, что есть в данных: обещать «бест-дилы», когда их
нет ни одного, значит показать пустую настройку.
